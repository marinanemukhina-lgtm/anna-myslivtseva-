# Подготовка российского PostgreSQL и безопасного переноса

Статус: локальная подготовка от PR21 `e773068380d2f7c4251e58c5515a9c3f1f5ecf65`. Никакой перенос, создание облачной БД/аккаунта/секретов, оплата, изменение production ENV, DNS, доступа или публикация не выполнены. Настоящие строки не читались и не копировались. Приведённые ниже шаги — план, а не разрешение выполнить их.

## Что решает адаптер

`server/postgres.mjs` использует официальный `pg` 8.23.1 и обычный PostgreSQL TCP-протокол с проверяемым TLS. Он не привязан к Neon HTTP и может работать с совместимым российским managed PostgreSQL. Конкретные провайдер, тариф, версия сервера, адрес, сертификат CA, сетевые ограничения и обработчики данных ещё должны быть утверждены. Например, Yandex Cloud Managed PostgreSQL документирует обычные PostgreSQL-подключения с доверенным CA, но эта ветка не создаёт там ресурсов и не подтверждает конкретный заказ или размещение.

- Если `DATABASE_DRIVER` отсутствует: прежнее поведение, `DATABASE_URL` выбирает Neon HTTP, отсутствие URL вне Vercel выбирает локальный SQLite.
- `DATABASE_DRIVER=postgres`: только прямой PostgreSQL. Нужен `DATABASE_URL` со схемой postgres/postgresql, явными пользователем/паролем/БД и без query-параметров или fragment. Строки подключения не помещать в чат, репозиторий или логи.
- Пустой/неизвестный явно заданный driver, отсутствующий URL или попытка SQLite на Vercel завершаются ошибкой; автоматического переключения на другую БД нет. Публичный fallback на initialContent сохраняется только при отсутствии DATABASE_DRIVER, а не при явном сломанном выборе; /api/session тоже показывает configured=false при таком состоянии.
- `DATABASE_TLS_CA_PEM` — необязательная публичная PEM-цепочка CA провайдера. Без неё используются системные доверенные CA. Всегда включены проверка цепочки, имени назначения и TLS >=1.2. `sslmode`, `sslrootcert`, `sslcert`, `sslkey` и другие URL-параметры запрещены, поскольку pg может переопределить ими TLS-настройки. `NODE_TLS_REJECT_UNAUTHORIZED=0` запрещён.
- Startup options явно задают search_path=public и не наследуют PGOPTIONS. Используется согласованная схема public; иные схемы требуют отдельной явной адаптации.
- Пул ограничен четырьмя соединениями на экземпляр процесса. Лимиты managed DB и число одновременно работающих API-экземпляров нужно согласовать до запуска; четыре соединения не означают четыре на весь сайт.
- `query` возвращает массив строк. `transaction` использует одно соединение, `BEGIN ISOLATION LEVEL READ COMMITTED`, последовательные запросы и `COMMIT`. Ошибка до COMMIT вызывает ROLLBACK; неопределённый COMMIT не повторяется автоматически и уничтожает соединение. Повторы callback должны сохранять прежний requestId.
- Существующая инициализация таблиц при старте приложения сохранена. Runtime-роли сейчас нужны соответствующие права: для least privilege следует отдельно согласовать отделение миграций от запуска. Нельзя обещать DML-only доступ, пока startup DDL остаётся в коде.

**БД в России сама по себе не локализует всю обработку.** Пока API принимает и обрабатывает запросы в США или иной стране на Vercel, телефон проходит через зарубежный сервер до записи в российскую БД. Нужно отдельно утвердить размещение API, обработку на CDN/WAF, доступы операторов, журналы/ошибки/аналитику, резервные копии, email/SMS и все другие получатели. Эта инженерная подготовка не является заключением о соблюдении законодательства. Публичный callback intake остаётся выключенным до отдельного решения по всему пути обработки.

## Инвентаризация без догадок о данных

По read-only metadata, переданной родителем 07.11.2026, в production сейчас есть `public.content`, `public.media`, `public.sessions`, `public.attempts`; все указанные поля NOT NULL. Callback-таблиц сейчас нет. Строки не читались. Перед реальным переносом нужен повторный утверждённый inventory схемы, индексов, ограничений, расширений, объёмов и зависимостей: новые/неизвестные таблицы нельзя молча пропускать.

| Объект | Что сохранить/решить |
| --- | --- |
| content(id text PK, body text, version int) | Все строки, не только main. Сохранить тело побайтно и версии. В main находятся профиль, услуги, новости, акции, дипломы, настройки bookingSchedule и приватное bookingOccupancy. В строке marketing находятся материалы/черновики. Нельзя переносить через publicContent(), который исключает частные поля. |

| sessions(id text PK, expires bigint) | Отдельное решение владельца: переносить действующие сессии либо завершить их. Отзыв не разрешён этой подготовкой. До любого отзыва подтвердить рабочий вход Анны в целевом окружении и независимый безопасный путь восстановления. При новом origin старые браузерные cookies и так не переносятся. |
| attempts(id text PK, count int, expires bigint) | Перенести действующие ограничения, если нет отдельного решения об их сбросе. Сброс может открыть новое окно перебора пароля. |

Сохранить идемпотентность, связь consent_version и действующие лимиты. Не запускать prune между сверками снимков. |

| Статические media, код и assets | Файлы `public/media`, `.media-parts`, собранные assets и документы, не лежащие в media, не входят в pg_dump. Перенести отдельно по проверенным manifest/checksum, сохранив права и URL. |

## Браузерные демонстрационные истории — отдельный путь

`src/ClinicalDemo.jsx` хранит карты, заметки и фотографии в localStorage текущего origin (`anna-open-synthetic-clinical-v1`), а не в Neon. Новый российский origin не увидит их автоматически. `pg_dump` не переносит эти фото/истории, localStorage, sessionStorage, cookies, незаписанные черновики, файлы телефона или голосовой ввод.

До смены origin владелец на каждом нужном устройстве должен закончить/сохранить текущие черновики и сделать инвентаризацию локальных материалов через существующий UI. Это не выполнено нами; личный браузер и реальные данные не открывались. Общий JSON export сохраняет весь demo state. ZIP export сохраняет только выбранную карту; существующий ZIP import **заменяет все карты**, а не объединяет их. Поэтому последовательный импорт ZIP не восстанавливает общую коллекцию. Нужно сохранить общий JSON и отдельные ZIP, проверить файлы вне браузера и не очищать старый origin.

Синтетический тест подтверждает полный JSON roundtrip через существующую функцию restoreClinicalDemo и ZIP roundtrip выбранной карты с фото/заметкой. Это не проверка пользовательского восстановления всей коллекции на новом origin: UI общего JSON import сейчас отсутствует. До настоящего cutover нужен отдельно согласованный и проверенный путь полного восстановления либо сохранение старого origin без потери доступа. Реальные медицинские данные нельзя переносить в этот открытый демо-раздел; если такие данные обнаружатся, остановиться и отдельно согласовать защищённую обработку.

## Локальные маркетинговые черновики и незавершённые операции

`server/marketing-assets/workspace.html` хранит локальную рабочую базу и workingDraft отдельно от серверной строки content/marketing. Есть JSON export (`kanal-progreva-baza.json`), проверяемый import и локальные backup keys перед загрузкой/импортом. Эти локальные черновики и backup keys не входят в pg_dump и не появляются на другом origin. Перед загрузкой серверной копии мастерская сама предупреждает о замене локальной базы. Нужно сначала сохранить/экспортировать актуальный рабочий текст на каждом устройстве, затем проверить синтетический roundtrip и отдельно согласовать конфликт локальной и серверной версии; нельзя считать серверную строку единственной или автоматически новейшей копией.

Callback retry metadata (не номер) хранится в sessionStorage и также привязан к origin. До переключения должны завершиться отправки с неопределённым исходом; перенос таблиц сохраняет серверную идемпотентность, но новый origin сам не восстановит прежний клиентский requestId. Не создавать новые заявки как «повтор» без выяснения прежнего результата. Незаписанные поля форм, загружаемые фотографии, текущий голосовой ввод, cookies/session tokens, настройки браузера, DNS/TLS и секреты окружения тоже вне pg_dump.

## Последовательность настоящего переноса: только после разрешения

1. **Выбрать целевую архитектуру.** Утвердить РФ-провайдера/регион/API, актуальную версию PostgreSQL, цену, договоры и получателей данных, TLS CA/hostname, резервирование/PITR/сроки, ключи и администраторов. Проверка источника сообщила PostgreSQL18; приёмник предпочтительно той же major-версии. Дамп из 18 в более старую версию не считать гарантированно совместимым. Никаких новых постоянных доступов без подтверждения.
2. **Репетиция на синтетике.** Отдельная пустая БД, отдельная роль, проверенный TLS, тот же schema/app release. Проверить restore, транзакции, конкурентный CAS/consent, дубли после потерянного ответа, rollback, кириллицу, base64 media, браузерные архивы и восстановление после перезапуска. Затем утвердить результаты и runbook с критериями stop/go.
3. **Подготовить права и копию.** Утвердить оператора миграции и временные минимальные роли. Экспорт и restore выполняются только в согласованном контуре, с шифрованием и ограниченным доступом к артефактам. Не выдавать runtime superuser. Не копировать владельцев, реальные credentials и grants автоматически. Сохранять схему/constraints/indexes осознанно; pg_dump не является экспортом всех cluster roles или настроек сервиса.
4. **Freeze перед окончательным снимком.** Согласовать окно и остановить все писатели: CMS/маркетинг, media, расписание/внутренние резервы, callback intake, session/login/logout, счётчики попыток, prune/автоматики и внешние интеграции. Просто спрятать кнопку недостаточно. Дождаться завершения начатых запросов. Записать исходный commit/schema и точное время. Не оставлять два активных писателя.
5. **Один согласованный снимок.** Использовать PostgreSQL18 pg_dump custom format в едином consistent snapshot либо эквивалентный проверенный способ. Финальный count/checksum manifest должен относиться именно к этому снимку/замороженному источнику. Для нескольких соединений использовать общий экспортированный snapshot, а не независимые несогласованные SELECT. Выгрузить все согласованные таблицы и данные; при schema drift или неизвестной таблице остановиться. pg_dump обеспечивает согласованность, но не забирает изменения после снимка: поэтому freeze критичен для отсутствия потерь.
6. **Restore в новый изолированный target.** Проверить архив, восстановить без автоматического переноса лишних owner/grants, затем установить согласованные права и ограничения доступа. Не запускать приложение на пустом target раньше restore, чтобы seed не замаскировал отсутствующие данные. При ошибке restore не продолжать поверх частично восстановленной БД: проанализировать и повторить в новом пустом target по разрешённому runbook.
7. **Сверка до переключения.** Сравнить все table counts и deterministic checksums, id/versions, content JSON и приватные booking поля, marketing row, ссылки media и реальные байты, callback consent/retry связность. Отдельно проверить восстановление сессий согласно выбранной политике, сроков и ограничений. `scripts/lib/migration-manifest.mjs` — чистая функция проверки явных row arrays, без подключения, экспорта или импорта; она не допускает неизвестные таблицы/поля и возвращает только агрегаты. Синтетические tests ловят потерю marketing, media corruption, приватных полей и версий. Настоящие manifests тоже хранить приватно; checksum сам по себе не доказывает правомерность переноса.
8. **Cutover.** После разрешения переключить только согласованные backend/адреса/ENV, проверить DNS/TLS и вход Анны, read-only страницы/медиа и защищённый список; запись проверить только утверждённым синтетическим тестом. Проверить доступность старых ссылок и локальных архивов. Открывать новые реальные записи только после отдельного go/no-go. Старую БД держать замороженной, не удалять.
9. **Rollback без потери новых записей.** До первой записи на target можно вернуть прежнюю конфигурацию, если это заранее согласовано. После появления новых записей нельзя просто переключить URL назад: сначала freeze target, сохранить и сверить его новые данные, согласовать обратную синхронизацию/merge и лишь затем переключать. Иначе потеряются новые media, настройки, заявки и статусы. Окно rollback, ответственный и критерии должны быть определены заранее.
10. **Закрытие.** После принятия результата утвердить хранение/удаление старой БД, экспортов, резервных копий и временных прав. Ничего не удалять и не отзывать автоматически. Проверить реальное восстановление backup, а не только наличие флага/заявленного retention. 6 часов Neon history retention из metadata не равны доказательству полного backup/restore или достаточного срока отката.

## Проверки этой ветки и ограничения

- Unit tests используют только явные synthetic config/номера/bytes и fake pool. Проверяют выбор драйвера, TLS downgrade, hostname mismatch, последовательность одной транзакции, rollback, потерянный COMMIT и отсутствие секретов в ошибках.
- `tests/postgres-native.test.mjs` требует отдельные POSTGRES_NATIVE_TEST_* параметры, literal loopback, фиксированные synthetic role/database/password и явный public CA; DATABASE_URL процесса запрещён. Проверяет настоящий PostgreSQL18/TLS, независимое соединение, CAS/rollback, реальное ожидание блокировки принятой политики, app-level driver dispatch/HTTP callback flow и recovery после фактически выполненного COMMIT с потерянным подтверждением. Без такого сервера тест честно skipped.
- `.github/workflows/native-postgres18.yml` подготовлен для будущего разрешённого CI: disposable official postgres:18-alpine, loopback port, однодневный synthetic TLS certificate, никаких реальных секретов/облачных ресурсов. Сам workflow не запускался этой локальной подготовкой.
- PostgreSQL18 и Docker/psql локально недоступны. Реальный PG18/native transport, российский target, его сеть/регион/права и полный restore **ещё не подтверждены**. Synthetic manifest/roundtrip — не заявление об уже выполненном переносе без потерь.
- Ветка явно запрещена для автоматического Vercel deploy. Никаких push/PR/merge/deploy не выполнялось.

## Локальный результат этой подготовки

Полный пакетный прогон с последовательным запуском и удалённой из процесса конфигурацией внешних БД: **205 passed, 0 failed, 3 skipped**. Три skips — существующие отдельные callback/booking PostgreSQL16 integration suites и новый PostgreSQL18/native TLS suite, которым не предоставляли настоящую БД. Маркетинговые проверки synthetic local/server draft preservation и клинические archive tests вошли в этот прогон. Проверка на физическом устройстве/новом origin и браузерный UI end-to-end в этой ветке не запускались. `npm run build` успешно завершён, `npm run test:sites`: 4 passed / 0 failed. `git diff --check` чистый.
