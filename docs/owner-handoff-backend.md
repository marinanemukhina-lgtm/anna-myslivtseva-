# Owner invitation handoff: explicitly disabled release preparation

This is code preparation, not authorization to initialize a real database, issue a real invitation, change a real password, or activate the feature in production. CI and local tests use synthetic credentials and disposable storage. This checked-in release is explicitly disabled. The active release has a browser claim page at `/admin/claim`; no invitation belongs in its URL.

## Security model

The only release selector is the reviewed source constant `OWNER_HANDOFF_MODE` in `shared/owner-handoff-mode.mjs`, currently `disabled`. Server, client, setup and initialization use this same module. It is not selected by an environment variable, database contents or request input. Unknown source values abort rather than select legacy mode. Activating requires a separate reviewed source change and build; deleting or changing `OWNER_HANDOFF_REQUIRED` can never change either release's mode.

**Disabled release:** exactly the legacy authorization and adapter behavior. Owner tables can be absent, empty, initialized, claimed, corrupt or incompatible without affecting authentication. There are no owner reads, DDL, writes, transaction guards, status/invitation/redemption handlers, claim UI or handoff setup warning. Owner initialization exits before importing the database client, opening a database, accessing the data directory or creating files, regardless of command arguments or environment variables. The ordinary legacy setup remains unchanged and does not inspect owner state. Existing content, media, sessions, approved temporary CMS/calendar access and private marketing boundaries are unchanged.

**Active release:** always requires valid durable owner state. Missing, malformed, incompatible or unavailable state fails closed, even when the opt-in flag is absent or `0`. Neither the environment password nor legacy sessions/temporary access are a fallback. Startup creates only empty owner tables, never an owner record or first-visitor setup. Active legacy request contexts are always denied at the mutation fence. Removing the owner row, owner schema or flag is not recovery.

A deliberate, separately authorized operator invocation of `node scripts/init-owner-handoff.mjs --initialize-existing-owner`, in an explicitly active source build, with `OWNER_HANDOFF_REQUIRED=1` as a separate operator acknowledgement and the explicitly selected deployment environment, copies the existing environment password hash into a new singleton. The script does not load `.env`, does not overwrite an existing row, and does not create or print an invitation. No such real invocation has been performed. Existing legacy sessions stop working immediately; the current owner must log in again. Initialization retains the specifically approved temporary CMS/calendar access until handoff completes.

The existing owner session and a fresh verification of the current owner password are both required to issue or revoke an invitation. Issue replaces any outstanding invitation. Only a SHA-256 digest of a random 256-bit invitation is persisted; the plaintext is returned once. Validity is fixed at 15 minutes. Tokens are never added to URLs, cookies or storage. Delivering the invitation to Anna requires separately authorized private communication; do not put it in chat logs, shell history, screenshots or analytics. Do not install body logging or response tracing on these endpoints.

Redeeming an invitation changes the scrypt password hash, consumes the invitation, increments the session epoch and sets the single temporary-access flag to closed in ONE atomic compare-and-swap update. Both CMS and calendar use that flag. No auto-login occurs. The new password must be 12–256 characters and differ from the existing password. All previous owner sessions are immediately invalid by epoch; environment-password fallback remains disabled. Unreferenced media also requires current owner access after handoff; intentionally published media remains public.

## API contract

All responses are no-store. Mutation endpoints use the existing same-origin JSON CSRF policy. Unknown request fields are rejected.

- `GET /api/owner-handoff`: `{enabled, configured, complete, mayIssue}`. Configured means valid durable state. No secret/hash parameters are exposed.
- `POST /api/admin/owner-invitation` with `{password}`: `{invitation, expiresAt}`. Existing owner session plus fresh password required; fixed 15-minute expiry.
- `DELETE /api/admin/owner-invitation` with `{password}`: `{revoked:true}` under the same authentication requirements.
- `POST /api/owner-handoff/redeem` with `{invitation,password}`: `{complete:true,loginRequired:true}`. Lowercase hexadecimal invitation; the UI normalizes pasted case.

Expected error bodies contain readable `error` plus stable `code`: `INVALID_INPUT` (400), `UNAUTHORIZED` (401), `INVALID_INVITATION` (409, including expired/unknown/replayed tokens), `HANDOFF_COMPLETE` (409), `RATE_LIMITED` (429), `HANDOFF_UNAVAILABLE` (503). All owner endpoints, including status, are absent (404) in a disabled release. Database/network/parser failures use the shared error handler; a 5xx or lost response may have an uncertain outcome. Do not automatically replay redemption after an uncertain result: check login/status instead.

Issuance/revocation share an eight-attempt/15-minute IP bucket. Redemption has a separate bucket. The counter is updated before scrypt work. Invalid token digest/expiry is checked before hashing. Existing login throttling remains in place. Reverse-proxy trust must continue matching the deployed platform; these limits are not a distributed abuse-prevention service.

## In-flight mutation protection

Authenticated and temporary middleware establishes a request-local access context. The database wrapper accepts only explicitly whitelisted mutations: version-CAS content updates (CMS, calendar, private occupancy and marketing), marketing seed insertion, and media insertion. Unknown mutations in this context fail closed. A stale owner context must match a current unexpired session and security epoch; a temporary context must match its epoch and the still-open flag. Legacy contexts are always denied in an active build, even when durable state is absent. Disabled builds do not enter this guard or establish handoff access contexts at all.

SQLite executes each guarded statement in synchronous `BEGIN IMMEDIATE` / commit without yielding. PostgreSQL executes `SELECT ... FOR UPDATE` on the security singleton then the guarded mutation as two statements in a `ReadCommitted` transaction. Transfer updates that same security row. Thus a writer ordered before transfer commits before transfer, and a writer ordered after it sees the closed flag/new epoch and changes no rows. A stale statement snapshot alone would NOT provide this guarantee, hence the explicit transaction and shared lock. Epoch-bound login insertion uses the same lock and matches the verified password hash.

Every authorized password rotation, recovery, or other access-changing security update MUST increment the epoch atomically. Direct manual partial edits, deleting the singleton, or changing credentials/access while retaining the epoch are prohibited operational procedures. Fresh requests reject malformed state; a request already authorized before an out-of-band same-epoch corruption is not protected against arbitrary database-administrator intervention.

Read requests authorized before transfer may finish delivering their already-read data; revocation does not retract bytes already delivered. The fence prevents late commits, not cancellation of every in-flight read. Initial activation is an operator migration and must occur with traffic drained: a not-yet-created singleton cannot supply a PostgreSQL row lock against legacy requests during first initialization.

## Release blockers and recovery

1. Obtain explicit authorization for deployment, production schema changes/initialization, invitation issuance and its recipient/delivery channel. None is authorized or executed by this local preparation.
2. Establish and verify external deployment/routing exclusions FIRST. **This disabled artifact is another legacy-capable binary, including as an immediate prior release or default rollback target.** It deliberately ignores owner state and cannot safely run after real activation. A durable row and this patch cannot secure an old binary or guarantee safe rollback. Exclude every legacy-capable binary (including this one) from automatic/manual rollback targets, production routing, direct deployment URLs, previews, background writers and old replicas. Prove every permitted rollback preserves active protection, and drain/remove legacy instances. If the platform cannot enforce this, do not activate or issue an invitation. Documentation alone is not enforcement.
3. Run the complete synthetic test suite and actual PostgreSQL integration suite against a disposable explicitly supplied test database. Verify the deployed adapter supports `ReadCommitted` transaction locking as used here. A skipped PostgreSQL suite is not a production pass.
4. Arrange a maintenance/drain window for initial durable-state creation, confirm the existing owner password hash and exact target out of band, and confirm the source build is active. The initializer additionally requires `OWNER_HANDOFF_REQUIRED=1`; that flag is not an application release switch. Do not initialize from an unauthenticated web route.
5. Confirm the owner can log in and use content/media/calendar with the current password before privately issuing an invitation. After redemption confirm old sessions/password fail, new owner login succeeds, and unauthenticated editors/unreferenced media are closed.
6. Keep database backups access-controlled. Do not roll back durable authentication state to an older credential/epoch. Recovery is a separately approved operation that must rotate credentials and epoch, revoke invitations, and preserve closed temporary access. No recovery bypass is provided. `scripts/setup.mjs` refuses legacy-only password changes in every active build without inspecting owner state. A disabled build cannot provide this protection, so it must be externally excluded after activation.

The temporary access source flags remain unchanged. Only an explicitly active server additionally gates the applicable paths with durable state.

## Local regression checks

- `npm test` includes a disabled matrix (owner tables absent/empty/unclaimed/claimed/corrupt/incompatible × `OWNER_HANDOFF_REQUIRED` unset/0/1), SQLite SQL interception, unchanged schema/sentinel checks, init filesystem/driver tripwires and a network-free real-Neon-client acknowledgement test. The matrix compares actual HTTP responses and legacy database results against local commit `f74255d513d4cdbdb1f210b546435a3d744714ab` when that exact commit is available. CI fetches full read-only history and requires that exact baseline; it fails if the commit is absent. Outside CI, tests explicitly report a missing differential comparison and independent expectations still run.
- Active security, init, Neon transport and PostgreSQL tests physically copy allowlisted source into isolated temporary trees and change only the reviewed mode literal to `active`. There is no runtime override in production. They retain invitation/session/epoch/fencing coverage and assert missing/corrupt/deleted/incompatible state and flag removal cannot restore legacy access.
- `npm run build` builds the disabled client. It must not emit a claim-page chunk or claim endpoint UI code. `npm run test:browser` verifies disabled routing and ordinary functionality; owner-claim scenarios explicitly skip there.
- `npm run test:owner-handoff-active-browser` builds a separate active source copy and runs the claim-page browser tests there. It never switches the checked-out release mode.
- PostgreSQL integration still requires the dedicated synthetic loopback database and explicit allow-write variables described in the tests. Mock Neon transport does not prove SQL execution, locking, durability or production compatibility.

No local test authorizes deployment. Disabled legacy behavior is independent of owner-table contents and therefore does not require resolving owner-table state or the database mapping to establish that behavior. Before any separately authorized disabled release, verify the target/current deployed baseline is the legacy f74255d5 behavior and that no real activation has occurred; this artifact must not replace an active release. Exact database mapping and initialization evidence are prerequisites for an active migration. An activation rehearsal must additionally verify drained requests, multiple replicas, old URLs and allowed rollback targets using actual platform controls; this source patch cannot prove those external exclusions.
